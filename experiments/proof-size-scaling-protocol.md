# Proof-size scaling protocol v1

Specified before the frozen corpus was run by the implementation, 10 September 2026. Experiment ID: `proof-size-scaling-v1`. Preserve this version after its freeze commit as `experiments/proof-size-scaling-protocol.md`. Design-time replicas of the generator and of the charge table, which are not the implementation, observed part of the content of claims 1 to 6 before the freeze; the section Pre-freeze observations lists exactly what they saw, and no claim in this document is described as specified before any run. The artifact is `artifacts/proof-size-scaling.json`, produced in replay mode by `peqnp proof-size-scaling [output.json] [--oracle-answers <path>]` from the committed oracle-answer file `artifacts/proof-size-scaling-oracle.json` (the default path, `oracle::answers_path("proof-size-scaling")`). The answer file is regenerated only by `peqnp oracle-answers proof-size-scaling [path]` on a machine with the pinned solver. Invocation, checkers, file formats, and the gate follow the merged reference-oracle design (PR #7: `src/oracle.rs`, `src/lrat.rs`, `src/sha256.rs`, the `scripts/check.mjs` preflight) as documented in `docs/oh.md` and the README; everything that design requires a protocol above 12 variables to state is stated here, with two declared deviations (a `theorem` reference kind and its validator) stated under Amendments to the reference-oracle design in the Reference model section and requiring independent reference-oracle review per `AGENTS.md` before the freeze commit.

## Question and distinct outputs

Every earlier corpus stopped at 12 variables and measured the cost of reading clues on formulas whose search was small. This experiment measures the other side of the program: how the repository DPLL's refutation size grows with the instance parameter on two families with proved resolution lower bounds, on random 3-SAT near the threshold, and on two controls whose exact tree size is predicted in advance. On pigeonhole it also measures two things that are easy to confuse and are reported apart: the effect on the same tree-like search of adding Cook's extension definitions to the formula (arm b, still tree-like resolution on a larger formula, not extended resolution), and the size and checking cost of Cook's supplied extended-resolution refutation (arm d, a checked proof, not a search). No result of arm (b) is evidence about extended resolution; only arm (d) is extended resolution, and it is supplied, not found.

Outputs are per case and arm: the outcome, one of `sat`, `unsat`, `unknown-budget`, `not-run`; the checked event counters; search nodes; the exact conflict count; and assignments. Per family and arm: a growth table over the family parameter with successive ratios and fixed-point log-log slopes as descriptive numbers. For pigeonhole: the line count and checking cost of the extended-resolution refutation. The proof-size proxies are search nodes and conflicts, not total events: the solver copies the formula at every restriction, so total events grow with formula size and search size together and are reported as cost. Every numeric quantity in the artifact is an integer, an exact rational pair of integers with a thousandths string (`RatioPair` `{"numerator":a,"denominator":b,"thousandths":"q.rrr"}`, computed by integer arithmetic exactly as `fragment::ratio` and `oracle::ratio_pair` do, round half up, `null` when the denominator is zero or on `u64` overflow of `a * 1000 + b / 2`, unreachable at these magnitudes since the largest numerator here is about `2 x 10^12`), or the signed variant `SignedRatioPair` `{"negative":false|true,"numerator":|a|,"denominator":b,"thousandths":"q.rrr"}` whose magnitude fields are the `RatioPair` of `|a|` and `b`, whose `negative` is true exactly when the signed quotient is strictly negative (a zero numerator is never negative), and whose `thousandths` string carries a leading `-` exactly when `negative` is true; the artifact contains no floating-point number, no wall-clock time, and no solver-reported statistic. The artifact's `experiment` field is the protocol id `proof-size-scaling-v1`, as every earlier artifact carries its protocol id; the answer file's `experiment` field is the registered name `proof-size-scaling`, as `scripts/check.mjs` requires, and the ledger records the answer file as `edition:proof-size-scaling-oracle-<sha256 of file bytes>`; the two strings differ by design and no validator expects them to agree.

## Solver and counters

The solver is an instrumented copy of `transfer::dpll` in `src/proof_size_scaling.rs`, unchanged in behavior (the same decisions and the same charged events): one search node per call; a formula check and one clause read per clause, repeated until no unit remains, restricting the formula by the first unit in list order; UNSAT on an empty clause; otherwise a branch on the lowest variable index in the remaining formula, positive literal first. Every restriction charges one assignment plus its clause and literal reads and writes. `transfer::validate`, `copy`, `dpll`, `decide`, and `solve` are not modified, so the six earlier artifacts cannot change; the copy is entered through its own `proof_size_scaling::decide` (validation with the lifted limit, one metered copy, then the copied `dpll`, the same sequence as `transfer::decide`), which every unqualified `decide` in this document names, and it lifts the 12-variable validation limit, carries an uncharged origin tag per clause (original or definition), an uncharged decision depth, and one uncharged derived counter, **conflicts**: the number of calls that return false on an empty clause. On every completed UNSAT case the tree is full binary (every leaf is an empty-clause return and every internal node has two children), so `search_nodes = 2 * conflicts - 1`; this identity follows from the code structure, and the experiment asserts it as an implementation check, not as a finding. By the standard translation of a decision tree into tree-like resolution (see Beame, Kautz, and Sabharwal for the form used here; the translation predates them), the trace with each unit propagation expanded into a branch whose other side is a leaf yields a tree-like refutation of at most `2 * assignments + 1` clauses, computed per completed UNSAT case from the residual meter's `assignments` (validation and copying charge none); this bound is loose by the decision count, since each decision charges two restrictions, and is reported beside the node count as an upper bound only.

For both Tseitin families and the parity family the experiment also records, per case, an uncharged **leaf-depth histogram**: the number of conflicts at each decision depth, where the decision depth of a leaf is the number of branch calls on the path from the root to that leaf (a conflict reached by propagation alone from the root has depth 0). Its JSON shape is an ascending array of `[depth, count]` pairs with nonzero counts only, so `[[15, 16384], [16, 32768]]` is the k = 28 entry of claim 2 and `[[21, 2097152]]` a single-depth entry; it has at most `3k/2 + 1` entries on a Tseitin case (decision depth never exceeds the variable count) and its total equals `conflicts`. It exists so that a deviation from claims 2 and 3, or from the parity implementation check, is explained by where the leaves lie, not merely flagged. **Partial records.** For an `unknown-budget` arm every charged counter, the leaf-depth histogram, the arm (b-after) mechanism counts, and the first-node indices are emitted with their values at exhaustion; the `outcome` field is what marks them partial, and no value is substituted. A `not-run` arm carries zero counters and `null` for every uncharged record.

## Interventions

**(a) DPLL as is.** `decide` on the original formula with the whole budget: validation with the lifted limit, one metered copy, then the solver. Preprocessing work is zero. Runs on every family. On the shared control PHP n = 3 this arm must reproduce the clue-transfer-v1 baseline counters exactly (below). Its **total events** are its one meter's `work_units`.

**(b) DPLL with Cook's extension definitions, pigeonhole only.** A family-specific shortcut: the definitions are the auxiliary variables of [Cook's 1976 proof](https://doi.org/10.1145/1008335.1008338) and encode knowledge of the family, not of the instance. Write `q^(n) = p` for the original variables of PHP(n+1, n). For each level m from n down to 2, for i in 1..m and j in 1..m-1, a fresh variable `q^(m-1)_{i,j}` is defined by

`q^(m-1)_{i,j} <-> q^(m)_{i,j} or (q^(m)_{i,m} and q^(m)_{m+1,j})`

as the four clauses `(-q^(m)_{i,j} or q^(m-1)_{i,j})`, `(-q^(m)_{i,m} or -q^(m)_{m+1,j} or q^(m-1)_{i,j})`, `(-q^(m-1)_{i,j} or q^(m)_{i,j} or q^(m)_{i,m})`, and `(-q^(m-1)_{i,j} or q^(m)_{i,j} or q^(m)_{m+1,j})`, in that order. Level m contributes `m(m-1)` variables and `4m(m-1)` clauses; all levels together add `(n-1)n(n+1)/3` variables, that is 8, 20, 40, 70, 112, 168, 240 for n from 3 to 9, and four times as many clauses, so the extended formula has `n+1 + n^2(n+1)/2 + 4(n-1)n(n+1)/3` clauses, that is 54, 125, 241, 413, 652, 969, 1375 for n from 3 to 9. The extended formula lists the original clauses first, then definitions by level from n down to 2, by (i, j) row-major within a level. Each definition introduces a fresh variable with an explicit definition, so the extended formula is satisfiable exactly when the original is; the case label applies to both.

Two numberings run, because the solver branches by index. **(b-before):** the extension variables are numbered first, level 1 first (`q^(1)_{1,1} = 1`, `q^(1)_{2,1} = 2`), then level 2 row-major, and so on, each level row-major, with the originals last as `p_{i,j} = offset + (i-1)n + j` where `offset = (n-1)n(n+1)/3`. **(b-after):** the originals keep their arm (a) indices and the levels follow from n-1 down to 1, row-major within each level.

The two-meter structure is that of `transfer::solve` for a library arm (a preparation meter, then a residual meter of `budget - preparation`); the preparation charges are these and not those of `transfer::preprocess`. A **preparation meter** charges: validation of the original formula (lifted limit); one metered copy (one clause read and one clause write per clause, one literal read and one literal write per literal), where in (b-before) the renumbering of each original literal is applied in that copy's literal write and charges nothing further; then one clause write per appended definition clause and one literal write per literal of that clause. The **residual meter** receives `budget - preparation` and runs `decide` on the extended formula: validation with the lifted limit, a second metered copy, then `dpll`. Preparation and residual work are reported separately, and the arm's **total events** are their sum; `search_nodes`, `conflicts`, and `assignments` are residual counters. Budget exhaustion in either meter is `unknown-budget`. The artifact stores the original clauses, the numbering rule, the extension clause count, and, under each numbering, the SHA-256 of `oracle::write_dimacs(extended, n(n+1) + (n-1)n(n+1)/3)` over the extended clauses in the stated order, not the extended clause lists.

The two numberings are treated differently: (b-before) carries a registered, falsifiable expectation, and (b-after) carries an implementation check. In (b-before) the solver never decides an original variable while a defined variable occurs in the remaining formula, and every decision on a defined variable is uninformed, so the expectation is that (b-before) is worse than (a), not better: more search nodes at every n where both complete. In (b-after) the decision tree is identical to arm (a)'s, by the following argument given here: original clauses contain no extension variable, so every unit on an extension variable comes from a definition clause and is entailed by the definitions with the current assignment to the originals; because the definitions are a conservative extension, a level-n definition clause is unit on an original variable only when it already contains a true literal, so no unit on an original variable is ever derived from a definition clause; and along any path decisions are made in increasing index order, so an original variable leaves every remaining original clause only by being assigned (for a pigeon i <= n the hole clause with the pigeon assigned true in hole j is the unit that assigns it; for pigeon n+1 the pigeon clause is satisfied only after rows 1 to n are assigned, when it is already empty), so the branch variable is the lowest unassigned original in both arms. Equal search nodes and conflicts at every n where both complete are therefore an implementation check under Acceptance, not a claim, and the artifact records per (b-after) case, not per node, two uncharged mechanism counts and two indices that the check requires to be 0 and `null`: the number of nodes at which a unit on an **original** variable was derived from a definition clause, and the number of nodes at which the branch variable was an original variable absent from every original clause of the remaining formula, each with the 1-based index in call order of the first such node, or `null` when the mechanism never fired. A node counts for the first mechanism when, in any propagation round of that node's call, the first unit in list order lies in a definition clause and its variable is one of the `n(n+1)` originals; each node counts at most once and the round is not recorded. A unit on an extension variable derived from a definition clause restricts no original clause and cannot change the branch choice while an original variable remains in an original clause, so it is not one of the two mechanisms the check requires to be absent; it is counted separately, by the same any-round rule, as a third uncharged count with its own first-node index, reported for completeness and used by no claim. No per-node list is emitted, so the record stays small at up to about `10^6` nodes; the artifact-size arithmetic is in the Artifact section. (b-after) therefore measures the carrying cost of the definitions per node. No theorem predicts a collapse under tree-like search on either numbering; the short extended-resolution proof is dag-like, and tree-like resolution is exponentially weaker than dag-like resolution on some families ([Ben-Sasson, Impagliazzo, and Wigderson](https://doi.org/10.1007/s00493-004-0036-5)). A negative result is consistent with theory and is reported as such.

**(c) Clause learning: not in this protocol.** A learning arm is a different solver with a dag-like proof and its own budget; it is deferred to a separate protocol identity so that this frozen document has no optional arm and its replay-time bound is complete. The artifact records `"learning_arm": false`, and the validator requires that literal.

**(d) Cook's refutation, pigeonhole only.** A supplied proof, not a decision procedure: the analogue of a clue from someone who knows the answer, reported to show the size a stronger proof system attains, with its checking cost. On the (b-before) formula, emit lemmas for each level m from n down to 2 in this nesting, which matches the hole-clause convention: j in 1..m-1 is the outermost loop; within each j, the pairs (i, k) with `1 <= i < k <= m` are visited in lexicographic order (i ascending, and k ascending within each i); for each pair, `H1 = (-q^(m-1)_{i,j} or -q^(m-1)_{k,j} or -q^(m)_{i,j})` is emitted and then `H2 = (-q^(m-1)_{i,j} or -q^(m-1)_{k,j})`, both before the next pair; after the last j, for i in 1..m, `P = (q^(m-1)_{i,1} or ... or q^(m-1)_{i,m-1})`; after the last level, the empty clause. So at level m the lemma sequence is `H1(1,2,j=1), H2(1,2,j=1), H1(1,3,j=1), H2(1,3,j=1), ..., H1(m-1,m,j=1), H2(m-1,m,j=1), H1(1,2,j=2), ...`, then `P(1), ..., P(m)`. The recorded lemma list is this sequence, and the artifact's arm (d) bytes depend on it. Only the `i < k` orientation of H1 is emitted; H2 passes by reverse unit propagation from that orientation alone (a reader may expect both orientations; the second is not needed). H1 propagates through the level-m hole clauses on j to the definition of `q^(m-1)_{k,j}`; H2 uses H1, both definitions, and the hole clauses on j and m; P uses pigeon clause i, the definitions, hole clause m, and pigeon clause m+1; below level n the hole and pigeon clauses are the previous level's H2 and P. The line count is `L(n) = 1 + sum_{m=2}^{n} (m(m-1)^2 + m) = n(n+1)(3n^2 - 5n + 8)/12`, so `L(3) = 20`, `L(4) = 60`, `L(5) = 145`, `L(6) = 301`, `L(7) = 560`, `L(8) = 960`, `L(9) = 1545`; this is an exact polynomial identity on a count fixed by the emission rule, verified by expanding the sum for n up to 12, and no growth-class label is attached to it or to any measured quantity.

Each lemma is checked by reverse unit propagation on a persistent clause list, never by copying. The checker is this protocol's own metered RUP checker, defined here; it is not `oracle::check_lrat`, which checks LRAT hints and charges no assignments, so arm (d)'s `Work` objects are not expected to match the shape or the charges of a `proof_check.work`. The **original clauses** of the check are the (b-before) extended formula. Arm (d) runs on one meter whose events are reported in three named phases, `initialization`, `array`, and `checking`, each a `Work` object, with the arm's **total events** their sum. **Initialization** is the clause list alone and charges exactly the events of arm (b-before)'s preparation meter on the same case and nothing else: validation of the original formula under the lifted limit (charged), one metered copy of the original clauses (one clause read and one clause write per clause, one literal read and one literal write per literal, the (b-before) renumbering applied in the literal write at no further charge), then one clause write per definition clause and one literal write per literal of that clause; the extended formula is neither validated nor copied a second time. Arm (d)'s `initialization` counters therefore equal (b-before)'s preparation counters (formula checks, clause reads, clause writes, literal reads, literal writes, assignments) at every n at which arm (b-before) ran, that is every n whose (b-before) outcome is `sat`, `unsat`, or `unknown-budget` (a `not-run` (b-before) arm carries zero counters and is not compared), and at every n from 3 to 9 equal the counts the rule fixes: with `C = n+1 + n^2(n+1)/2` original clauses, `Λ = n(n+1)^2` original literals, and `E = (n-1)n(n+1)/3` definitions of 11 literals each, formula checks 0, clause reads `2C`, literal reads `2Λ`, clause writes `C + 4E`, literal writes `Λ + 11E`, assignments 0, work units `3C + 3Λ + 15E`, that is 330, 735, 1383, 2331, 3636, 5355, 7545 for n from 3 to 9; the artifact asserts both as implementation checks, and the assignment array is not part of either. **Array** is the assignment array of one cell per variable of the extended formula, initialized with one literal write per cell and nothing else, so the `array` phase is exactly `(n-1)n(n+1)/3 + n(n+1)` literal writes, that is 20, 40, 70, 112, 168, 240, 330 for n from 3 to 9, and the artifact asserts that count as a second implementation check; the empty trail belongs to this phase and charges nothing until an entry is written. **Checking** is everything from the first lemma's emission on. For each lemma in emission order: (1) emission charges one clause write and one literal write per literal of the lemma; a lemma containing a repeated or complementary pair of literals is malformed and invalidates the run. (2) For each literal of the lemma, assign its negation true, charging one assignment and one literal write for the trail entry. (3) Propagate in passes over the clause list in order: one formula check per pass; per clause one clause read, then its literals left to right, one literal read each, stopping at the first literal true under the assignment; if no literal is true and no literal is unassigned, the clause is falsified and the lemma **passes**: the pass ends at that clause and no further clause of the list is read; if no literal is true and exactly one is unassigned, assign that literal true, charging one assignment and one literal write for the trail entry, and continue the pass; otherwise continue. A pass that assigns nothing and falsifies nothing means the lemma **fails**, which invalidates the run. (4) Undo the trail, one literal write per entry. (5) Append the lemma to the clause list (already charged in step 1). The final empty clause is checked from the empty assignment and must be falsified by propagation alone. Every charge is a formula check, clause read, clause write, literal read, literal write, or assignment; there are no search nodes in arm (d). The checker runs `L(n)` lemma checks over a clause list that starts at the `n+1 + n^2(n+1)/2 + 4(n-1)n(n+1)/3` extended clauses and grows by at most `L(n)` lemmas, so its total is polynomial in n, which the measured counts illustrate and do not prove.

## Fixed corpus

Random draws use the xorshift64 transition `x ^= x << 13; x ^= x >> 7; x ^= x << 17` on a 64-bit unsigned state with truncating shifts; `next()` applies the transition and returns the new state (`transfer::Rng`).

**XOR encoding.** A parity constraint over d variables `v_0 < v_1 < ... < v_{d-1}` (ascending index) with charge c is encoded as the `2^(d-1)` clauses forbidding each assignment whose XOR differs from c: for s from 0 to `2^d - 1` in ascending order, where bit j of s (0-based) is the value assigned to `v_j`, emit a clause exactly when the number of set bits of s has parity different from c; that clause lists the literals in ascending variable order, the literal on `v_j` being positive when bit j of s is 0 and negative when it is 1. This is the ternary-cube convention of `transfer.rs` (`signs & 1` is the first variable, positive when zero). The clause set is determined by the constraint; this order fixes the clause order, which the solver's first-unit restriction depends on.

- **Pigeonhole PHP(n+1, n)**, n from 3 to 9. Variables `p_{i,j} = (i-1)n + j` for pigeon i in 1..n+1 and hole j in 1..n. Clauses: for i in 1..n+1 the pigeon clause `(p_{i,1} or ... or p_{i,n})`; then for j in 1..n and i < k the hole clause `(-p_{i,j} or -p_{k,j})`, j outermost, (i, k) lexicographic. Variables `n(n+1)`, that is 12, 20, 30, 42, 56, 72, 90; clauses `n+1 + n^2(n+1)/2`, that is 22, 45, 81, 133, 204, 297, 415. Every case is unsatisfiable by the pigeonhole principle. **Shared control:** n = 3 is byte-identical (declared variables and ordered clause list) to clue-transfer-v1's `pigeonhole-4-3` (`src/transfer.rs`, `p*holes+h`, hole clauses `for h { for a { for b > a }}`); it is kept deliberately as the one shared control, exempt from the overlap rule, because it is the family's truth-table calibration point and it pins arm (a) to a published counter set.
- **Tseitin on a seeded 3-regular graph**, k vertices for even k from 4 to 40. Half-edges `0..3k-1` belong to vertex `floor(h/3)`. Initial state `5003 XOR (k << 32)`. Each attempt starts from the identity array `0..3k-1` and shuffles it by Fisher-Yates from position `3k-1` down to 1, drawing `j = next() % (i+1)` and swapping positions i and j; positions 2t and 2t+1 are paired into an edge. Reject the pairing if it has a loop, a repeated edge, or is disconnected; on rejection increment the rejection count, reset the array to identity, and shuffle again from the continued generator state (the state is never reseeded). Edges sorted by (min endpoint, max endpoint) get variables 1.. in that order; vertex 0 has charge 1 and every other vertex charge 0; clauses by vertex 0..k-1, each vertex's constraint over its three incident edge variables in ascending index, four clauses per vertex. Variables `3k/2`, clauses `4k`; k = 4 is K4. The total charge is odd, so every case is unsatisfiable. Fixture expectations under this rule, computed by a reference script before the freeze and required of the implementation: k = 4 gives K4, edges `(0,1),(0,2),(0,3),(1,2),(1,3),(2,3)`, after 19 rejections; k = 6 gives edges `(0,3),(0,4),(0,5),(1,2),(1,3),(1,5),(2,4),(2,5),(3,4)` after 24 rejections. The graph is expander-like by construction only; its edge list and rejection count are preserved and no expansion is certified. One graph per k: event totals on this family describe that one graph and are not averaged. **Triangle inventory and rejection counts**, computed before the freeze by a script that reimplements the rule above and reproduces both fixtures: the frozen graphs contain, as (vertex, vertex, vertex) triples, k = 4: four triangles (K4); 6: (0,3,4), (1,2,5); 8: (1,5,6), (2,3,7); 10: (1,2,4), (3,7,9); 12: (1,2,4); 14: (1,7,8), (3,9,13); 16: (3,4,6); 18: (2,3,6); 20: none; 22: (2,7,15), (5,12,20); 24: (2,4,23); 26: (5,12,20), (7,9,22); 28: (0,9,11), (2,15,22), (6,12,26); 30: (4,15,23); 32: none; 34: (0,21,24), (12,26,30); 36: (2,11,28); 38: (19,25,37); 40: (10,31,39). Rejection counts under the rule are 19, 24, 4, 16, 2, 5, 16, 0, 30, 2, 14, 0, 10, 8, 9, 30, 2, 8, 4 for k = 4 to 40 in steps of 2; only the k = 4 and k = 6 values are fixtures required of the implementation by test, the rest are pre-freeze observations recorded so that a differing graph is recognised as a generator discrepancy before any counter is compared, and a discrepancy is resolved by the rule stated under claim 2. A triangle is necessary for the extra-decision mechanism described under claim 2 but not sufficient: seventeen of the nineteen graphs contain one, and only k = 28 shows a second leaf depth in the pre-freeze simulation. Expected exhaustion points under the pre-freeze replica are in the Pre-freeze observations section: k = 34 is the last seeded size expected to complete under the `10^9` budget, k = 36 is expected to be `unknown-budget` by a margin of about 5 percent, and k = 38 and 40 `not-run`; a completed k = 36 would require the implementation to charge fewer events than the replica, which the shared-control equality makes unlikely, and either outcome leaves the bound of one full-budget run per family and arm unchanged.
- **Tseitin on the prism, non-expander control**, k vertices for even k from 6 to 40. The prism CL(k/2) has outer vertices `0..k/2-1`, inner vertices `k/2..k-1`, outer edges `(i, (i+1) mod k/2)`, inner edges `(k/2+i, k/2+((i+1) mod k/2))`, and rungs `(i, k/2+i)` for i in 0..k/2-1; k = 4 is excluded because CL(2) has repeated edges. It is 3-regular, simple, and connected. Its treewidth is at most 4 for every k in range: eliminating vertices in the order `1, k/2+1, 2, k/2+2, ..., k/2-1, k-1, 0, k/2` never eliminates a vertex with more than four remaining neighbours, checked by script at every even k from 6 to 40 before the freeze; it is exactly 3 at k = 6 and 8 and exactly 4 at k = 10, 12, 14, and 16 by an exhaustive elimination-order computation validated on known graphs (cycle 2, K4 3, 3 by 3 grid 3, 4 by 4 grid 4, Petersen 4), so the bound 4 is tight from k = 10 on and 3 would be false there. Bounded treewidth gives resolution refutations of size polynomial in k, and the graph is not an expander. Edge numbering, charges, clauses, variable and clause counts are exactly as for the seeded family. Every case is unsatisfiable. Its expected exhaustion point under the pre-freeze replica is also k = 36; the replica completes k = 34 at 965,336,168 events, about 3.5 percent under the `10^9` budget, so an implementation charging slightly more than the replica would make k = 34 `unknown-budget` and k = 36 `not-run`, and either outcome leaves the bound of one full-budget run per family and arm unchanged and is not a discrepancy.
- **Random 3-SAT at ratio 4.26**, n in `10, 12, 16, 20, 24, ..., 64` (fifteen sizes), base seeds `9001, 9007, 9011, 9013, 9029, 9041, 9043, 9049`, `m = (426n + 50) / 100` clauses in integer division, that is 43, 51, 68, 85, 102, 119, 136, 153, 170, 187, 204, 222, 239, 256, 273. Initial state `s XOR (n << 32) XOR (m << 40)`, this protocol's own seed rule, stated in full here; it is not `fragment::effective_seed`, whose rule is `base_seed XOR (n << 32) XOR (t << 40) XOR (b << 48)`, and a reader should not look for it in `fragment.rs`. Draw each clause with `fragment::draw` (made `pub(crate)`): draw `next() % n + 1`, reject a repeated variable, draw the sign from a fresh draw's low bit, zero meaning positive, stop at three literals; clauses may repeat. 120 cases; labels come from the reference after every arm has returned, and satisfiable and unsatisfiable cases are reported as separate series. The ratio 4.26 is the rounded crossover estimate of Crawford and Auton (4.258); Mitchell, Selman, and Levesque reported about 4.3. At n <= 40 this DPLL needs at most a few hundred conflicts on every seed under the pre-freeze replica, so the lower half of this family is primarily a control on the oracle path and the median machinery; only the upper sizes can show growth, and their series are thin (below).
- **Doubled parity chain**, n from 4 to 30. Variables `x_i = i` for i in 1..n, `t_i = n + i` and `u_i = 2n - 2 + i` for i in 1..n-2. Constraints, each encoded as above over its variables in ascending index: `x_1 xor x_2 xor t_1 = 0`, `t_{i-1} xor x_{i+1} xor t_i = 0` for i in 2..n-2, then `t_{n-2} xor x_n = 0`; the same chain over u with final constraint `u_{n-2} xor x_n = 1`. Variables `3n - 4`, clauses `8(n-2) + 4` (20 at n = 4); every case is unsatisfiable, since the two chains sum to `x_1 xor ... xor x_n = 0` and `= 1`. With x numbered first, the solver's tree is fixed by the branching rule: no constraint becomes unit until two of its variables are assigned, deciding `x_1` propagates nothing, deciding `x_{i+1}` for i in 1..n-3 propagates `t_i` and then `u_i` and nothing else, and deciding `x_{n-1}` propagates `t_{n-2}`, then `x_n` from the t chain's final constraint, then the u chain's `u_{n-2}` against its final constraint, which is falsified; so every path decides exactly `x_1..x_{n-1}`, every leaf is a conflict at decision depth `n-1`, and `conflicts = 2^(n-1)` with `search_nodes = 2^n - 1`. That count is a consequence of the fixed corpus and the solver's rule, so it is an implementation check under Acceptance, not a claim. The family has linear-size dag-like refutations that resolve the two chains against each other in constant width, and it also has tree-like refutations of size polynomial in n: a decision tree that queries the variables of a middle cut of the ladder and recurses into the half whose chain values disagree has depth logarithmic in n (an argument given here, not a cited result). Gaussian elimination over GF(2) decides it in a number of bit operations cubic in n. The `2^(n-1)` tree therefore separates the fixed branching order from tree-like resolution as well as from dag-like resolution; the family exhibits no tree-like versus dag-like separation.

Enumerate families in this order and sizes ascending, seeds inner for random 3-SAT. Within each structured family and arm, after the first `unknown-budget` size, larger sizes are recorded as `not-run`; within each random 3-SAT seed and arm, after the first `unknown-budget` size, larger sizes of that seed are `not-run`. This is a budget policy, never a decision, and it bounds the number of full-budget runs at one per structured family and arm and one per random seed. Only an arm's own budget exhaustion triggers it; an unknown label never does, and a case whose arms are all `not-run` is still labelled. Reject exact `(declared_variables, ordered_CNF)` overlap between cases and with the six earlier corpora `unit-propagation-calibration-v1`, `clue-transfer-v1`, `indexed-transfer-v1`, `implication-calibration-v1`, `fragment-interface-v1`, and `extraction-cost-v1`, each regenerated from code at replay (`two_variable_formula(mask)` for the 65,536 calibration formulas, whose two declared variables make that comparison vacuous but uniform, and `transfer::corpus`, `indexed::corpus`, `implication::corpus`, `fragment::corpus`, and `extraction::corpus`) and never parsed from artifact JSON, with exactly one exemption, the shared control PHP n = 3 from clue-transfer-v1 named above; the check runs on every case and the exemption is recorded in the artifact as `"shared_controls":[{"case":"pigeonhole-4-3","corpus":"clue-transfer-v1"}]`. The corpus has 191 cases: 7 pigeonhole, 19 seeded Tseitin, 18 prism, 120 random 3-SAT, 27 parity. Sizes above 12 variables are in scope because the reference no longer requires a truth table; they remain a finite range, not asymptotic evidence.

## Reference model

Reference model string: `"truth-table<=12;definition;theorem:pigeonhole-structural,xor-gf2;oracle:cadical-3.0.1+model-check+lrat-check"`, the reference-oracle design's string with this protocol's `theorem` segment inserted. Per-case `reference` objects are tagged `truth-table`, `definition`, `theorem`, or `oracle`; the first, second, and fourth are exactly the merged design's objects and are validated by the unchanged `oracleReference`; the third is defined here and validated by `theoremReference`, specified below.

**Amendments to the reference-oracle design.** The merged design labels a case above 12 variables by definition or by the oracle and validates `reference` rows with `oracleReference`. This protocol deviates in two declared ways and in no other. (1) The report's `reference_model` string carries the segment `theorem:pigeonhole-structural,xor-gf2` between `definition` and `oracle`; the frozen `REFERENCE_MODEL` constant in `scripts/oh-report-checks.mjs` and the string the demo replay writes are unchanged, and this protocol's validator compares against its own constant. (2) `scripts/oh-report-checks.mjs` gains `theoremCertificate` and `theoremReference` beside `oracleReference`, specified below; `oracleReference` itself is unchanged and still validates every truth-table, definition, and oracle row of this artifact. No `Label` variant is added: `oracle::Label`, `oracle::Summary`, `Summary::json`, the answer-file format, the LRAT checker, the solver pin, and the byte-compared demo fixture `tests/oracle/demo-reference.json` are untouched. The theorem label lives in this experiment's own module `src/proof_size_scaling.rs` as `CaseLabel { Design(oracle::Label), Theorem(TheoremCertificate) }`; the design's `Summary` receives only the `Design` labels through `Summary::include`, so its `cases` counts 128 (24 truth-table and 104 oracle cases), and the module emits a sibling object `theorem_summary` `{"theorem_cases":63,"pigeonhole":6,"tseitin":32,"parity":25}` with the implementation check `summary.cases + theorem_summary.theorem_cases = 191`. Under `AGENTS.md`, both deviations are reference-oracle changes requiring independent reference-oracle review, separate from the review of this protocol, before the freeze commit; no other existing validator or artifact sees the new kind.

**Truth-table cases (at most 12 declared variables), 24 cases:** PHP n = 3; seeded Tseitin k = 4, 6, 8; prism k = 6, 8; random n = 10, 12 (16 cases); parity n = 4, 5. The reference is the existing exhaustive truth table via `oracle::label`, reported outside every arm with its model count, label, and backbone.

**Definition cases:** none expected. No generator here emits an empty clause or an empty formula; a `definition` row is a generator bug and invalidates the run.

**Theorem cases (structured families above 12 variables), 63 cases:** pigeonhole n = 4 to 9, seeded Tseitin k = 10 to 40, prism k = 10 to 40, parity n = 6 to 30. The label is fixed by a cited theorem and an in-repo structural check outside every arm, never by a solver, and these cases never call `oracle::label`, are never written to DIMACS, and have no answer-file entry. Pigeonhole: unsatisfiable by the pigeonhole principle (Haken's paper states the formula; the principle is elementary); the structural check verifies the variable and clause counts, `n+1` pigeon clauses each of n distinct positive literals covering row i, and all `n(n+1)/2` hole pairs for each hole, in the stated order; every completed arm (d) check is an additional certificate, since a reverse-unit-propagation derivation of the empty clause from the conservatively extended formula refutes the original. Tseitin and parity: the clause encoding of an XOR constraint is exact (a clause set on d variables with `2^(d-1)` forbidden assignments has exactly the constraint's solutions), so the case is a GF(2) system; the theorem is the charge-sum argument (summing every vertex constraint cancels each edge twice and leaves `0 = 1` when the total charge is odd; for the parity chain, summing both chains leaves `0 = 1`). The structural check, outside every arm, first **decodes the XOR system from the emitted clause list**, never from the generator's constraint list: the case's clauses are partitioned in order into consecutive groups whose widths follow the family's constraint sequence (four clauses per vertex for both Tseitin families; for the parity chain, four clauses for each ternary constraint and two for each binary one in the stated order); each group must be exactly the `2^(d-1)` forbidding clauses of one constraint over one ascending variable tuple in the stated encoding order, the tuple being read off the group's first clause and the charge off which sign patterns occur, and the tuple and charge re-encoded by the XOR encoder for clause-by-clause comparison; a group that is not such an encoding invalidates the run, and so does a decoded system that differs from the generator's constraint list in any tuple, charge, or position, which is a generator bug. Gaussian elimination over GF(2) then runs on the decoded system, records the rank and, on an inconsistent system, the certificate: the list of decoded-row indices whose sum is `0 = 1`, re-verified by a separate routine that XOR-sums the listed decoded rows. Every structured case, including those at or below 12 variables, carries a `structure` object with this check; at or below 12 variables the truth table is the label and the structure check must agree with it. The reference's row operations are a descriptive count outside every arm, not events. `reference` for a theorem row is `{"kind":"theorem","label":"unsat","family":"pigeonhole"|"tseitin"|"parity","certificate":{...}}` with the structural counts or the GF(2) row list.

**`theoremCertificate(certificate, family, row)` and `theoremReference(reference, row)` in `scripts/oh-report-checks.mjs`,** added beside `oracleReference` for this protocol's ledger validator and used by every future validator that carries theorem rows (frozen validators stay untouched). `theoremCertificate` carries no variable bound and recomputes every certificate field from `row.input` and `row.variables` rather than trusting it. Pigeonhole rows: the certificate is `{"n","variables","clauses","pigeon_clauses","hole_pairs"}`; the routine solves `row.variables = n(n+1)` for the integer n, requires `row.input.length === n+1 + n^2(n+1)/2`, regenerates the `n+1` pigeon clauses and the `n^2(n+1)/2` hole clauses in the stated order, and requires `row.input` equal to that list clause for clause and the certificate's counts equal to the recomputed ones. Tseitin and parity rows: the certificate is `{"constraints","rank","rows"}`; the routine decodes the XOR system from `row.input` by the same grouping rule as the Rust check (group widths from the family and the variable count: `k = 2 * row.variables / 3` vertices of four clauses each for Tseitin, and for parity `n = (row.variables + 4) / 3` with, per chain, `n-2` ternary groups of four followed by one binary group of two, the t chain then the u chain), requires every group to be an exact encoding, requires `constraints` to equal the number of decoded rows, then XOR-sums the decoded rows listed in `rows` (each index in range, listed once) and requires the result to be the empty variable set with charge 1, that is `0 = 1`; then runs its own Gaussian elimination over GF(2) on the decoded rows (`BigInt` bitsets; the largest system in the corpus, parity n = 30, has 58 rows over 86 variables, and the largest Tseitin case 40 rows over 60) and requires `rank` to equal the recomputed rank, so no field of the certificate is accepted on trust. `theoremReference` requires `kind === "theorem"`, `label === "unsat"`, `family` in `{pigeonhole, tseitin, parity}`, and `row.variables > 12`, then calls `theoremCertificate`. The validator calls `theoremCertificate` on the `structure` object of every structured case at or below 12 variables, requires that check to pass and its verdict `unsat` to agree with the case's truth-table row's label; a structured case at or below 12 variables whose `reference.kind` is not `truth-table`, or a theorem row at or below 12 variables, is rejected. The report's `reference_model` must equal the string above, and `theorem_summary.theorem_cases` must equal the number of theorem rows.

**Oracle cases (random 3-SAT above 12 variables: n from 16 to 64, 104 cases):** the reference is the declared oracle of the reference-oracle design, CaDiCaL 3.0.1 (pinned binary SHA-256 `601c9fa8ba5d09fd81bb00c89b3e54832f138bccc3422bd8652e8cda4d74d1fa`), invoked exactly as the merged `src/oracle.rs` does on the case's raw clauses written by `write_dimacs` with the declared variable count, under a **conflict limit of 100,000** (`Limits { conflicts: 100_000 }`), the only oracle limit, never a time limit. A SAT answer is a label only after `check_model` verifies the model against the raw clauses; an UNSAT answer is a label only after `check_lrat` verifies the LRAT proof (RUP with hints, deletions honoured, final empty clause required). The per-entry proof cap is 2,097,152 bytes and the answer-file cap is 16,777,216 bytes, both as sizing constraints; a conflict-limit exit or a proof over the cap labels the case **unknown** (`reason` `conflict-limit` or `proof-over-cap`), and the case stays in the artifact with its arm results, is excluded from every comparison and from both random series, and is never re-drawn. An invalid model, an invalid proof, a parse or exit anomaly, a missing, duplicate, or unused entry, an identity or limit mismatch, or a file over the cap is an error that stops the run and names the digest; none of these is ever a label. **Composed calls:** none; no backbone or sampling query is made, so `oracle_calls` equals `oracle_cases`. **Expected entries:** exactly 104, one per oracle case (the overlap rule forbids two cases with one digest). **Expected file size:** no pre-freeze regeneration was run and no answer-file size was measured; a design-time probe of the pinned solver's interface, recorded under Pre-freeze observations and stated in no repository document, gave 9,577 bytes for one random n = 60 proof of 146 lemmas and 725,182 bytes for PHP(8,7). The pre-freeze DPLL labels (Pre-freeze observations) give 35 unsatisfiable and 69 satisfiable oracle cases; a satisfiable entry is a model of at most 64 integers, so the file exceeds the 16,777,216-byte cap only if the unsatisfiable proofs average above 479,000 bytes, about fifty times the measured n = 60 proof. If that happens, `write_answers` refuses the file and regeneration fails with `FileCap`, an error and never a label, and the top random size is removed under a new protocol identity, never silently; a single proof over 2,097,152 bytes is a `proof-over-cap` unknown, not an error. No structured case, no arm (b) formula, and no pigeonhole formula of any size is ever sent to the solver. Because `oracle::regenerate` solves every case its registered corpus function yields above 12 variables that is not a definition case, the `proof-size-scaling` entry of `oracle::EXPERIMENTS` registers a **separate regeneration corpus function** that yields only the 104 random 3-SAT cases with n >= 16, in corpus order, and no structured case and no random case at or below 12 variables; the replay driver builds the full corpus separately and labels structured cases by the theorem path. The `AnswerUnused` check then makes the committed file contain exactly those 104 entries, and a structured entry in the file (a pigeonhole formula at n = 7, PHP(8,7), would be an entry of 725,182 bytes as measured by that probe, and at n = 8, PHP(9,8), expected about 7 MB by extrapolation and hence a proof-over-cap unknown) is refused as unused before any comparison. The driver looks up a case's entry only after every arm has returned for that case; arm modules do not import `oracle`. **Driver contract.** The `proof-size-scaling` driver does not use `oracle::replay_cases`, which calls `oracle::label` on every case and would stop the run with `AnswerMissing` at the first structured case above 12 variables. It first requires the answer file's `experiment` field to equal `proof-size-scaling`, as `replay_cases` would. It runs every arm on every case; then, per case and only after every arm has returned, it labels a case at or below 12 variables through `oracle::label` (the truth table), a structured case above 12 variables through the theorem path without touching `oracle::label`, the answer file, or the `used` set, and a random case above 12 variables through `oracle::label` with the shared `used` set; after the corpus it calls `oracle::check_used` once over that set, which the random cases alone have built, so the committed file must hold exactly the 104 random entries. The protocol's driver-order test is its own, not the design's `replay_cases` test: a recording arm on a corpus containing all three case kinds proves that no `label` call and no theorem check precedes the return of every arm on that case, and that no structured case reaches `label`.

## Growth statistics

For each family and arm, take the completed cases ordered by the family parameter (n for pigeonhole, random 3-SAT, and parity; k for both Tseitin families). For random 3-SAT, each label series takes, at each size, the **right-censored median over the s seeds carrying that label**: sort the completed values ascending, append one entry of positive infinity per `unknown-budget` or `not-run` seed of that label, and take the entry at 1-based position `ceil((s+1)/2)` (so the upper median for even s, never an average); the median is defined exactly when at least `ceil((s+1)/2)` seeds completed, is reported with s and the counts of completed, unknown, and not-run seeds, and is otherwise `unknown`. A point with s < 3 is reported and flagged `thin`. Cases with an unknown label belong to neither series and count in neither s.

Report the series for search nodes, conflicts, assignments, and total events (arm (d) has an events series only), and for each pair of **adjacent sizes of the family's size list at which both points are defined**: the **successive ratio** `S_{i+1} / S_i` as a `RatioPair`, and the **fixed-point log-log slope** `(L(S_{i+1}) - L(S_i)) / (L(x_{i+1}) - L(x_i))` as a `SignedRatioPair` over the magnitudes, where `L` is the following integer base-2 logarithm with 24 fractional bits. A ratio or slope never spans an undefined, `unknown`, `unknown-budget`, or `not-run` size; where either endpoint of an adjacent pair is undefined the ratio and slope are `null`, and the ledger validator checks the `RatioPair` and `SignedRatioPair` shapes with `BigInt` (the rules stated under Question and distinct outputs, recomputed). For an integer `S >= 1` let `e` be its bit length minus 1; let `Y = S * 2^(60-e)` when `e <= 60` and `Y = floor(S / 2^(e-60))` otherwise; then for b from 1 to 24: `Y = floor(Y^2 / 2^60)` in 128-bit arithmetic, and if `Y >= 2^61` set bit `24-b` of the result and halve `Y` by floor division; `L(S) = e * 2^24` plus the bits set. So `L(1) = 0`, `L(2) = 16777216`, `L(3) = 26591258`, `L(4) = 33554432`. A ratio or slope with a zero denominator or a zero log argument is `null` and the point is kept: satisfiable random cases can complete with zero conflicts, so the conflicts series has `null` ratios and slopes at such points and no value is substituted. These are descriptive numbers on a finite range: a finite series is consistent with polynomials of high degree and exponentials of small base alike, no fitted curve is reported, no series is labelled polynomial-like or exponential-like, and no claim is made that the range distinguishes the two. For pigeonhole, also report at each n the exact rational ratios of (a) events to (d) events first, then (a) search nodes to (d) lines, with the events comparison stated before the lines comparison in every table and summary. For the two Tseitin families, report the ratios of conflicts and of event totals between the prism and the seeded graph at each k where both complete, as descriptive `RatioPair`s; no equality between the two graphs is claimed.

## Claims under test

Each claim is falsifiable on the finite range by the stated numeric criterion; a claim whose criterion cannot be evaluated because the relevant cases are unknown is reported as not evaluated, never as passed. Every claim is descriptive with a registered threshold or an exact prediction; no statistic here has a null hypothesis beyond the stated threshold. No falsification below invalidates the run, and no criterion coincides with an acceptance condition: the identities, the fixed counts, and the shared-control equality are implementation checks under Acceptance, not claims.

1. **Pigeonhole, arm (a), descriptive with a registered threshold.** The successive ratio of conflicts from n to n+1 is at least 4 at every completed step from n = 3 upward. Falsified by one step below 4. The threshold 4 is registered below every pre-freeze ratio (5.7 to 11.6 at n = 3 to 8) so that the claim fails only on a qualitative change in the implementation's counts, on which alone it is evaluated; a criterion that conflicts exceed `2^n` at every completed n >= 4 is not registered because the shared control fixes 9 conflicts at n = 3 and `9 * 4^(n-3) > 2^n` for every n >= 4, so it could never fail first. Haken's theorem is asymptotic with unstated constants and predicts no number at these sizes; it lower-bounds the tree-like refutation, hence assignments through the `2 * assignments + 1` translation, and bounds search nodes only through the per-path propagation factor of at most `n(n+1)` restrictions per node. No counter here is checked "against" the theorem.
2. **Seeded Tseitin, arm (a), registered leaf-depth histogram.** The claim is a registered table of leaf-depth histograms, one per completed k: at every completed even k from 4 to 40 except k = 28, the histogram is `{k/2 + 1: 2^(k/2 + 1)}` (every leaf at decision depth `k/2 + 1`, hence `conflicts = 2^(k/2 + 1)`); at k = 28 it is `{15: 16384, 16: 32768}` (49,152 conflicts). Falsified by any completed k whose histogram differs from the registered entry, in either direction. The count itself is not the claim: on a completed UNSAT case the tree is full binary, so every leaf at one depth d forces exactly `2^d` leaves by arithmetic, and the empirical content is which k satisfy the single-depth condition. Motivation, not definition: with edges numbered by sorted endpoints, when every vertex constraint is resolved only by unit propagation forcing its third edge once two are assigned, each branch assigns by decisions exactly the complement of a spanning tree, so the leaves are indexed by the cyclomatic number `|E| - |V| + 1 = k/2 + 1`; a vertex whose three edges are all assigned by other vertices' propagation (for instance a triangle whose outer edges are fixed while free edges remain) is falsified before the last vertex on half the branches and on the other half is satisfied without forcing anything, so those branches need one more decision. The table's basis is the pre-freeze replica, which observed every entry and extrapolated none; the triangle inventory of every frozen graph is recorded in the corpus entry so that a deviation is checkable against the triangle mechanism, and the entries at k = 36, 38, and 40 are expected to be unevaluable (`unknown-budget` or `not-run`) under the `10^9` budget and are registered so that a completed case there meets a prediction made before the freeze. The empirical content of the frozen run is whether the implementation's histograms agree with an independent reimplementation at every completed k. **Discrepancy rule.** A deviation at any k is first checked as a possible generator discrepancy: the prose rule of this protocol is authoritative; the implementation is corrected only where it departs from the prose (the fixtures at k = 4 and 6 are required by test, and the recorded rejection counts and triangle inventory are compared at every k), never to reproduce the pre-freeze script's output; the script's SHA-256 is recorded in the freeze commit message and the script is kept as a design artifact outside the crate, as evidence about the table's origin and never as an authority over the implementation. If the implementation conforms to the prose and its histogram still differs from the table, the claim is reported falsified at that k with the histogram and the graph's triangles, and the table is never adjusted; if the pre-freeze script is found to have departed from the prose, that is recorded beside the verdict. This series measures the cyclomatic number under one branching order, not expansion; agreement is not evidence about Urquhart's theorem, whose bound concerns every resolution refutation and whose hypothesis (expansion) is uncertified here.
3. **Prism control, arm (a), exact prediction.** `conflicts = 2^(k/2 + 1)` with a single-depth leaf histogram on every completed k, on a graph with polynomial-size resolution refutations; no proof of the single-depth condition is given for the prism, and the pre-freeze replica observed it at every k from 6 to 40. Falsified by any completed k with a different count or histogram, reported as a falsification and never as an invalidating condition, with the same discrepancy rule as claim 2; the leaf-depth histogram is recorded so that a falsification is explained by where the leaves lie. No equality between the prism and the seeded family is claimed: conflicts and event totals of the two graphs at each k where both complete are reported as descriptive ratios.
4. **Random 3-SAT, arm (a), registered thresholds.** Evaluated only on points with s >= 3 for every median involved. (i) At every size where both label-series medians of conflicts are defined, the unsatisfiable median is at least the satisfiable median; falsified by one size where the strict reverse holds. The direction is registered because a satisfiable case can stop at its first model while an unsatisfiable case must close every branch; that is a reason, not a theorem. Under the pre-freeze replica (i) holds at every evaluable size (12, 36, 44, 48, 52, 56, and 64; n = 60 has a thin satisfiable point; the table under Pre-freeze observations lists both medians and their s at each of these sizes). (ii) The unsatisfiable median of conflicts at n = 64 is at least 4 times the unsatisfiable median at n = 36, decided by cross-multiplication of the integer pairs; evaluated only when both medians are defined with s >= 3, and otherwise reported as not evaluated. Falsified by a ratio below 4. The threshold 4 is registered below the replica's 1793/158 (thousandths 11.348) so that the claim fails only on a qualitative change in the implementation's counts or in the oracle's labels; the per-pair ratios are reported as descriptive numbers and carry no criterion, for the reason stated in the Pre-freeze observations. Under the pre-freeze labels, the sizes 36, 44, 48, 52, 56, 60, and 64 carry at least three unsatisfiable seeds, so both endpoints of (ii) are expected to be defined; an oracle unknown at either endpoint removes that seed from s and can make (ii) not evaluated. More seeds are not registered under this identity because each seed adds one potential full-budget run to the replay bound; a wider seed set belongs to a new protocol identity.
5. **(b-before) versus (a).** Search nodes of (b-before) exceed those of (a) at every n where both complete; falsified by one such n with (b-before) at or below (a). The pre-freeze replica gave 147 versus 17 at n = 3 and 11,155 versus 103 at n = 4 and exhaustion at n = 5, so the expected series is two points.
6. **Arm (d) against arm (a).** Arm (d)'s total events are below arm (a)'s total events at every completed n >= 5. Falsified by one such n where the inequality fails. The threshold is registered at the crossover the pre-freeze replica observed (events 283,806 against 435,578 at n = 5, with (d) above (a) at n = 4), so the claim fails on any shift of the crossover upward. The ratio of arm (a)'s conflicts to `L(n)` (375 against 145 at n = 5 under the replica) is reported as a descriptive number and carries no criterion, because claim 1 with the shared control already implies conflicts of at least `9 * 4^(n-3)`, above `L(n)` at every n >= 6. The check's passing and its line count are implementation checks under Acceptance, not part of this claim. The crossover n at which (d) events first fall below (a) events is reported as a bounded observation.

No P versus NP claim follows from any outcome. Whether a search procedure finds a short proof is a separate question from whether one exists; arm (d) exhibits existence on one family, and arms (a) and (b) measure one search procedure's behavior on a finite range.

## Limitations

Finite ranges and one uninformed branching order; per-node cost grows with formula size, so event totals mix proof size and instance size; arm (b) supplies family knowledge and cannot generalize, and (b-after) measures carrying cost only, since its tree is arm (a)'s by construction; the seeded graph is not a certified expander, and the count of claim 2 is a property of the branching order and the edge numbering under a hypothesis that the graph can violate, so this experiment says nothing about expansion; one graph per k makes Tseitin event totals descriptive of that graph; claims 2 and 3 were observed in full by a pre-freeze replica, so the frozen run tests the implementation's agreement with an independent reimplementation rather than an unobserved prediction; the random 3-SAT medians rest on at most eight seeds per size, split by label after the arms ran, with unknown-label cases in neither series, the unsatisfiable series rests on three to six seeds at the evaluable sizes and on one or two at the others, and claim 4(ii) rests on two endpoints; the lower random sizes are too easy for this DPLL to show growth; UNSAT labels above 12 variables on random cases rest on a checked LRAT proof from one pinned binary, which is a verified certificate and not a second opinion; the oracle's conflict limit and proof cap can leave the top of the random range unknown, the `10^9` budget can leave it `unknown-budget`, and no size is re-drawn. Everything measured is bounded-tested; the exponential lower bounds and the polynomial extended-resolution upper bound are cited theorems, not results of this experiment.
