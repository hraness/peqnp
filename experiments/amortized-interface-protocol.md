# Amortized interface protocol v1

Specified before the frozen corpus was run by the implementation, 10 September 2026; the paragraph on pre-freeze observations at the end of the claims section lists exactly what design-time runs saw. Experiment ID: `amortized-interface-v1`. Preserve this version after its freeze commit. The crate and the gate key this experiment by the one name `amortized-interface`: the artifact is `artifacts/amortized-interface.json`, produced by the replay command `peqnp amortized-interface` from the committed oracle-answer file `artifacts/amortized-interface-oracle.json`, whose `experiment` field is `amortized-interface` and whose regeneration command is `peqnp oracle-answers amortized-interface`. The artifact's own `experiment` field carries the experiment ID above, as the earlier artifacts carry theirs. This is a finite experiment protocol; it makes no claim about P versus NP.

## Question and distinct outputs

The repository's [knowledge-and-complexity framework](../docs/knowledge-and-complexity.md), in its section on loading, persistence, and what counts as a step, records what is settled about charging the load of an algorithm and its background knowledge: a fixed library is part of the program, so loading it costs a constant that can change the constant of a bound and never its exponent; and knowledge that is allowed to depend on the input length is advice, the class P/poly, which is believed not to contain NP because [Karp and Lipton](https://doi.org/10.1145/800141.804678) showed that if it did the polynomial hierarchy would collapse to its second level. Two terms are left open there, and this experiment measures both. The first is amortization: persistent memory is a genuine shortcut for the total cost of many related instances, never for the worst case of one, and every earlier experiment here charged its interface once per formula. The [extraction-cost experiment](extraction-cost.md) ended with the observation that forced literals of the binary fragment shorten the search but their read costs more than the cut, so a positive delta from clues needs an interface whose build cost is already paid. The second is the framework's measurable version of the argument that one load step unlocks embedded algorithms that lower the cost of every later step: a persistent library is described by its build cost, its length, and the residual per-instance cost it leaves against the plain baseline that never builds it; amortization alone leaves that residual ratio bounded below by a constant across input sizes, whereas a library that does more than amortize would show the ratio falling with n. This protocol registers both a break-even count and a signed per-n comparison of that ratio, each with a numeric criterion.

This experiment pays the build once. A **query family** is one fixed binary fragment together with k distinct ternary remainders; each query is the fragment conjoined with one remainder. The interface of the fragment (its implication graph, components, certificate, and settled extraction of every forced literal) depends on the fragment alone, so it can be built once per family and reused by every query. The first question is the **break-even query count**: after how many queries does building the interface once repay itself against the plain solver that never builds it. Against the fresh arm that rebuilds the interface per query the answer is fixed by accounting, as the next section derives, and is an implementation check rather than a claim. Knowledge compilation asks the same question, compiling a theory once so that many later queries are cheap ([Darwiche and Marquis](https://www.cs.cmu.edu/afs/cs.cmu.edu/project/jair/pub/volume17/darwiche02a.pdf)); here the compiled form is the fragment interface, the query is a SAT decision on the fragment plus a remainder, and every cost is an event in the declared model. The second question is whether the persistent arm's per-instance cost, with the build excluded and the per-query accounting margin removed, falls relative to the plain solver as n grows across the range this laboratory can reach.

Three arms decide every query, each under one budget of 4,000,000 declared events per arm run:

1. **Arm A, fresh:** the extraction-cost settled arm, unchanged: fragment graph construction on the query formula, components, fragment certificate, settled extraction, copy of the query with its forced literals appended as units in the order `1, -1, 2, -2, ...`, then the residual DPLL. Every phase is charged per query. A fragment UNSAT certificate returns UNSAT with no extraction, append, or residual.
2. **Arm B, persistent:** once per family, on the fragment formula alone: construction, components, certificate, and settled extraction, charged once as the **persistent build**. Per query: read the store, copy the query, append the stored units with the clue-transfer append charges, and run the same residual DPLL. Nothing else is charged per query and nothing is stored between queries beyond the family's interface. The exact charging is in the next section.
3. **Arm C, plain:** the existing deterministic unit-propagation/DPLL solver on the query formula, per query. The word fresh is reserved for arm A and plain for arm C throughout.

For each family, report the cumulative work of each arm after q queries for q = 1..k, the break-even query counts at which arm B's cumulative work first falls strictly below arm A's and strictly below arm C's, or `never within k`, the persistent build cost, the unit count, and the store size. Families whose fragment has an UNSAT certificate answer every query from the store without residual and form a separate stratum. Families whose fragment is satisfiable are split by whether the fragment forces at least one literal. Report per stratum before any aggregate. Per n, in the forced stratum, report the residual ratios defined in the claims section and their signed differences between successive n.

No truth table, reference label, reference backbone, or oracle value reaches any arm. The arms use no learned library; the implication-graph procedures are fixed algorithmic knowledge with no acquisition step. The store of arm B is not advice: its content is a function of the family's fragment, an input, and is built by an arm at charged cost, never supplied by input length.

## Query families and the three arms

**Formulas.** A family has declared variables n, binary count b, ternary density t, and base seed s. Its **fragment formula** F is the list of b width-two clauses drawn as described in the corpus section, over n declared variables, with clause indices `0..b-1`. Its k **remainders** R_1..R_k are lists of `t*n` width-three clauses each. **Query j** is the ordered CNF `F ++ R_j`: the fragment clauses at indices `0..b-1`, then the remainder at indices `b..b+t*n-1`. This layout differs deliberately from the earlier generators, which emitted ternary clauses first: with the fragment as the prefix, a clause index cited by a path in the family's store is the same index in every query formula, so the raw checker validates the stored paths against every query without translation. The binary fragment of query j, in the sense of the fragment-interface protocol, is exactly F with its indices.

**Arm A.** Per query, `extraction::solve_settled(query_j, n, budget)` on a fresh meter: construction (`build_fragment`, which validates the whole query formula with one formula check, one clause read per clause and one literal read per literal, then one clause read per clause for the width check, then constructs the graph with one clause read per clause, two literal reads per binary clause, and the edge writes of the implication-calibration protocol), components, decision certificate, settled extraction exactly as the extraction-cost protocol states it, then the append phase (the clue-transfer copy of the query formula: one clause read and one clause write per clause, one literal read and one literal write per literal; then per forced literal one literal read, one clause write, and one literal write) and the residual (`transfer::decide` on the processed formula: validation, copy, and the common DPLL). Phases are reported separately as in the extraction-cost artifact, and the per-query total A_j is the sum of the six phases: construction, components, certificate, extraction, append, residual. If the certificate is not SAT, the arm returns UNSAT after the certificate phase and the later phases are idle.

**Arm B, the persistent build.** Once per family, on its own meter with the same 4,000,000-event budget: `build_fragment(F, n, meter)` with the fragment as its only formula input, `components`, `decision_certificate`, and, when the certificate is SAT, `settled_extract`, each charged exactly as in arm A but on F, which has b clauses and no ternary clause. The result is the family's **store**: the certificate; when SAT, the ordered clue list in the order `1, -1, 2, -2, ...` with each clue's literal and its path over indices of F; and nothing else. Store construction is the only event-charged work that happens per family rather than per query. The build cost P is the sum of its phases: construction, components, certificate, and extraction when the certificate is SAT; construction, components, and certificate otherwise. Because F is the binary fragment of every query with the same indices, the graph, components, certificate, and clues that arm A computes on any query are the same objects, which acceptance asserts field by field; the only difference in charge is construction, where arm A reads the `t*n` ternary clauses of the query and the persistent build does not. Per ternary clause arm A charges one clause read and three literal reads in validation, one clause read in the width check, and one clause read and no literal read in graph construction, six events, so arm A's construction exceeds the persistent construction by exactly `6*t*n` events, an identity acceptance also asserts.

**The driver.** The replay driver runs `oracle::replay_cases` over the 1,920 queries in protocol order with a closure that sees only `(input, n)`. The closure does not recognise F inside a query: it keeps a family cursor over the frozen corpus, and on the first query of each family in protocol order it builds that family's store from the family's F, which the corpus constructor supplies beside the query list. The fragment formulas F are never entries of the oracle corpus list `Experiment.corpus`: that list holds exactly the 1,920 queries, so no F at 16 or 20 variables can receive an answer-file entry.

**Arm B, per query.** On a fresh meter with the 4,000,000-event budget:

- If the stored certificate is not SAT: charge one scalar read (literal-read category) of the stored verdict and return UNSAT. No copy, append, or residual runs. The per-query work is exactly 1.
- If the stored certificate is SAT: charge one container read (clause-read category) of the stored clue list; then the append phase exactly as arm A charges it, with the stored units in the stored order: the clue-transfer copy of the query formula and, per stored unit, one literal read, one clause write, and one literal write; then the residual, `transfer::decide` on the processed formula. The per-query work is therefore `B_j = 1 + append + residual`, and when arm A completes the same query its append and residual counters are identical to arm B's, which acceptance asserts.

**What persists and what does not.** The store holds the certificate and the clue list with paths. It is written once by the build and read only afterwards; no query writes to it. Nothing from one query's residual reaches another: the residual DPLL runs on a per-query copy, returns only an outcome and counters, and no assignment, learned clause, restriction, or intermediate formula from one query is retained. Every per-query run of arm B is a pure function of the store and the query formula. That the store depends on F alone is established by the build's inputs, the fragment F and n and nothing else, by the exact `+6*t*n` construction identity, and by the store-equals-arm-A check on every query; the focused test that permutes a family's query order demonstrates the absence of shared mutable state between queries and is kept as a regression check. **Store size** is reported per family as `store_cells`, defined exactly: for a SAT store, `n + Σ_clues (1 + |nodes| + |clauses|)`, the certificate's n values plus, per clue, its literal, its path nodes, and its cited clause indices; for an empty-clause certificate, 1, the clause index; for an opposite-paths certificate, `1 + Σ_{two paths} (|nodes| + |clauses|)`, one cell for the verdict plus the nodes and cited clause indices of both paths. A SAT store has at most n clues, each with a simple path of at most 2n nodes and at most `2n - 1` clause indices, so `store_cells <= n + n*(1 + 2n + 2n - 1) = n + 4n²`.

**Arm C.** Per query, `transfer::solve(query_j, n, None, budget)` on a fresh meter: validation, copy, and the common DPLL. Its per-query work is its residual, `C_j = validate(query_j) + copy(query_j) + dpll_C_j`.

**Cumulative work and break-even.** For a family with per-query totals A_j, B_j, C_j and persistent build P, define in checked `u64` arithmetic `A(q) = Σ_{j≤q} A_j`, `B(q) = P + Σ_{j≤q} B_j`, `C(q) = Σ_{j≤q} C_j`. The break-even against A is the least q in `1..k` with `B(q) < A(q)`, and against C the least q with `B(q) < C(q)`; ties do not count; when no such q exists the value is `never within k`. Both are defined only for comparable families, below. On comparable families report also `ratio_pair(B(k), A(k))` and `ratio_pair(B(k), C(k))` as descriptive thousandths, and `P` itself.

**Accounting identities.** From the definitions above, whenever arms A and B both complete query j: in the satisfiable strata `A_j = construction_A + components + certificate + extraction + append + residual = (P + 6*t*n) + append + residual`, and `B_j = 1 + append + residual`; in the `fragment-unsat` stratum `A_j = P + 6*t*n` and `B_j = 1`. In every stratum, therefore,

`B_j = A_j - P - 6*t*n + 1`, and summing, `B(q) = A(q) - (q - 1)*P - q*(6*t*n - 1)` for every q in `1..k`, so `B(1) = A(1) - 6*t*n + 1`. In the `fragment-unsat` stratum the sums have the explicit forms `B(q) = P + q` and `A(q) = q*(P + 6*t*n)`, which satisfy the same identity.

Since `6*t*n` is at least `6*3*8 = 144` on every family, `B(1) < A(1)` on every comparable family in every stratum, and the break-even against A is 1 everywhere by construction. Arm A is dominated by its per-query construction; the comparison against arm A therefore carries no information beyond these identities, which acceptance asserts exactly, and only the comparison against arm C is a measurement.

Against arm C the per-query margin is defined once. With u the number of stored units, `m = b + t*n` clauses and `L = 2b + 3*t*n` literals in the query, the clue-transfer copy of the query costs `2m + 2L = 6b + 8*t*n` events; the append adds `3u`; the residual's validation and copy of the u appended unit clauses add `2u + 4u = 6u` over arm C's validation and copy of the query alone. Hence

`B_j - C_j = M + (dpll_B_j - dpll_C_j)`, with the per-family constant `M = 1 + 6b + 8*t*n + 9u`,

and `B(q) < C(q)` iff `Σ_{j≤q} (dpll_C_j - dpll_B_j) > P + q*M`. The break-even against C is the least q at which the cumulative DPLL saving from the stored units exceeds the build plus q margins. M ranges from `241 + 9u` at `n = 8, t = 3, b = 8` to `1,001 + 9u` at `n = 20, t = 4, b = 60`. In the `unforced` stratum `u = 0` and the processed formula equals the query, so `B_j = C_j + 1 + 6b + 8*t*n` exactly and `B(q) - C(q) = P + q*(1 + 6b + 8*t*n) > 0` for every q; that stratum's break-even against C is `never within k` by construction and is an implementation check. The quantities the experiment does not know in advance are the DPLL savings `dpll_C_j - dpll_B_j` on forced families, whether their sum over q queries exceeds `P + q*M` for some `q <= k`, and how the persistent arm's per-instance cost compares with arm C's across n.

**Decomposition of the per-instance ratio.** Over any set of comparable forced families, with `S_B = Σ_families Σ_{j≤16} B_j`, `S_C = Σ_families Σ_{j≤16} C_j`, and `S_M = 16 * Σ_families M`, the identity above sums to `S_B = S_C + S_M - Σ_families Σ_{j≤16} (dpll_C_j - dpll_B_j)`, and `S_B - S_M = Σ (validate(query_j) + copy(query_j) + dpll_B_j)` is a sum of nonnegative counters, so the checked subtraction `S_B - S_M` never underflows. Three ratios over the common denominator `S_C` are reported: the **residual ratio** `r = ratio_pair(S_B, S_C)`, the persistent arm's per-instance cost with the build excluded, against the plain solver; the **margin term** `m = ratio_pair(S_M, S_C)`, the part of r that the store read, the copy, and the unit appends contribute by construction; and the **DPLL ratio** `r_d = ratio_pair(S_B - S_M, S_C)`, the part that the residual search contributes. Their numerators satisfy `numerator(r) = numerator(r_d) + numerator(m)` exactly in integers; their thousandths may differ from the sum of thousandths by one through rounding. The margin term falls with n by construction, because M grows linearly in n while `C_j` grows faster (the extrapolation under budget and replay time puts the fall between n = 8 and n = 20 at roughly 40 to 50 thousandths on the `b = n` composition), and is not the phenomenon Claim 2 tests; Claim 2 is registered on `r_d`.

## Fixed corpus

**Generator.** All random clauses use the xorshift64 transition `x ^= x << 13; x ^= x >> 7; x ^= x << 17` on a 64-bit unsigned state with truncating shifts, returning the new state. For base seed s, declared variables n, ternary density t, and binary count b, the initial state is `s XOR (n << 32) XOR (t << 40) XOR (b << 48)`, the existing `fragment::effective_seed`; the fields occupy disjoint bits for this domain. Draw a clause of width w by repeating: draw `next() % n + 1` as a variable, reject it if it already occurs in the clause, and once accepted draw its sign from a fresh draw's low bit, zero meaning positive; stop after w accepted literals. From one generator per family, emit the b binary clauses of F first, then k blocks of `t*n` ternary clauses, block j being R_j, in that order. Clauses may repeat within a formula. The k remainders must be pairwise distinct as ordered clause lists; a repeat invalidates the corpus (`transfer::Failure::InvalidInput`, which the registered corpus function maps to `OracleError::Parse` naming the family) and is never repaired by re-drawing.

**Families.** Base seeds `9001, 9007, 9011, 9013`; declared variables `8, 10, 12, 16, 20`; ternary densities `3, 4`; binary counts `n, 2n, 3n`; `k = 16` queries per family. That is 4 × 5 × 2 × 3 = **120 families** and **1,920 query cases**, 24 families per n and 8 families per `(n, b)`. Family id `family-n{n}-t{t}-b{b}-s{s}`, query id `family-n{n}-t{t}-b{b}-s{s}-q{j}` for j in `1..16`. Enumerate seeds outermost, then n ascending, then t, then b, then j. The 72 families with `n <= 12` (1,152 queries) are labelled by the truth table; the 48 families with n in `16, 20` (768 queries) are labelled by the oracle.

The generator does not enforce a satisfiable fragment. Whether F is satisfiable, and whether it forces a literal, is decided by the arm's checked certificate and clue list and defines the strata: `fragment-unsat` (the certificate is an empty clause or opposite paths), `forced` (SAT certificate, at least one clue), and `unforced` (SAT certificate, no clue). Random 2-CNFs with `b = n` lie near the satisfiability threshold and those with `b = 3n` are almost always unsatisfiable, so the strata are unbalanced across b; stratum sizes are reported and no claim assumes them. Sizes at 8 to 12 variables are calibration sizes chosen so the truth table stays feasible, and 16 and 20 are oracle sizes chosen so the replay bound holds; none is scaling evidence.

**Stratum sizes expected from the pre-freeze simulation.** The strata are a consequence of the fixed corpus, and a reimplementation of the generator with a transitive-closure classifier of the fragment (a design-time script outside the repository, run on 10 September 2026 before any arm existed) put them at 46 `forced`, 14 `unforced`, and 60 `fragment-unsat` families, with no repeated remainder; per n as forced, unforced, fragment-unsat: 6, 6, 12 at n = 8; 11, 4, 9 at n = 10; 10, 2, 12 at n = 12; 10, 1, 13 at n = 16; 9, 1, 14 at n = 20; per b: 25, 14, 1 at `b = n`; 20, 0, 20 at `b = 2n`; 1, 0, 39 at `b = 3n`. The forced families with `b = n` number 2, 4, 5, 7, 7 at n = 8, 10, 12, 16, 20, with unit counts in enumeration order `4, 1`; `1, 1, 1, 1`; `1, 2, 2, 1, 2`; `3, 4, 4, 6, 2, 2, 5`; and `3, 9, 1, 2, 1, 1, 1`; over all forced families the unit count ranges from 1 to 14. These are pre-freeze expectations, reported beside the crate's counts; the crate's counts stand whatever they are, and a difference is examined against the generator rules above before publication, as the implementation checks state.

**Freshness.** Reject any exact `(declared_variables, ordered_CNF)` overlap between query formulas, between fragment formulas, or between either and the corpora of the six earlier experiments: unit-propagation calibration (the 65,536 formulas over the sixteen canonical clauses on two variables, enumerated and compared like the others rather than recorded as disjoint by construction), clue-transfer, indexed-transfer, implication-calibration, fragment-interface-v1, and extraction-cost-v1 primary; and against the three demo oracle fixtures. There are no shared controls. The check is run by the corpus constructor before any arm runs and the artifact records `exact_earlier_overlap: 0` as the result of the comparison.

## Reference, budgets, and accounting

**Reference model:** `truth-table<=12;definition;oracle:cadical-3.0.1+model-check+lrat-check`, exactly as the merged reference-oracle design (`docs/oh.md`, README) defines it. For n at most 12, the independent truth-table evaluator enumerates all `2^n` assignments of each query after the corpus is fixed and records the model count, the label, and the exact backbone when the model count is positive. For n in `16, 20`, every query is looked up in the committed answer file and re-verified on every replay: a `sat` entry is accepted only after its model satisfies every raw clause of the query, an `unsat` entry only after its LRAT proof passes the repository's std-only checker (RUP with hints, deletions honoured, the last lemma the empty clause). No query is a definition case: every query has `b + t*n >= 32` clauses and no empty clause, so `definition_cases` must be 0. There are no composed calls; no backbone is computed above 12 variables.

**Oracle limits:** one conflict limit, `conflicts = 100000`, for every entry; never a time limit. The per-entry proof text cap is 2,097,152 bytes and the answer-file cap is 16,777,216 bytes, as `src/oracle.rs` fixes them in `PROOF_TEXT_CAP_BYTES` and `ANSWER_FILE_CAP_BYTES`. **Expected entries: exactly 768**, one per oracle query: the oracle corpus list holds exactly the 1,920 queries and never a fragment alone, regeneration skips the 1,152 queries at or below 12 variables, distinct ordered CNFs over the same n have distinct DIMACS texts and therefore distinct digests, and the corpus freshness check guarantees distinctness. `check_used` verifies that every committed entry was used at least once; the stronger statement that every entry is used exactly once holds because the 768 digests are distinct, so each query looks up its own entry and no entry serves two queries. **Sizing.** The committed proof fixtures are 389 bytes at 16 variables and 68 clauses (`tests/lrat/p16-1.lrat`), 929 bytes at 30 variables and 128 clauses (`tests/lrat/p30-1.lrat`), and 5,604 bytes at 60 variables and 300 clauses (`tests/oracle/p60.lrat`); at 16 to 20 variables and 64 to 140 clauses every proof is therefore expected under 8,192 bytes, and with about 300 bytes of entry framing the file is expected under `768 × 8,500 = 6,528,000` bytes, under 8 MiB and far under the 16,777,216-byte cap; no conflict-limit unknown is expected. An unknown, if one occurs, labels that query `unknown`, keeps it in the artifact with its arm results, excludes it from every comparison, and is never re-drawn. A file over its cap stops regeneration and is reported as a sizing failure of this protocol, not repaired by dropping cases.

**Unknown cases.** An arm run that exhausts its budget is `unknown`, with its spent budget reported and no certificate, clue, or outcome. A query is comparable when all three arm runs completed and its label is `sat` or `unsat`. A **family is comparable** when its persistent build completed and all k of its queries are comparable; cumulative curves, break-evens, and claims use comparable families only. A family whose persistent build is unknown has no certificate and therefore no stratum; such families form a fourth bucket, `build-unknown`, reported outside the three strata with the same per-n counts, and the per-stratum tables carry only families with a certificate. On the queries of a `build-unknown` family arms A and C run as on every query, arm B does not run, and each query record carries `arm_b: null`; the family record carries the build's spent budget and no cumulative array for B. Non-comparable families with a certificate are listed in their stratum's tables with every reason that applies (`arm-A-unknown`, `arm-B-unknown`, `arm-C-unknown`, each with the query indices, and `label-unknown` with the query indices), and the count of families under each reason is reported per stratum and per n. For a non-comparable family whose build completed, the **comparable prefix** is the number q* of leading queries in protocol order that are comparable; the family's three cumulative arrays truncated to length q* (empty when q* = 0), and its break-evens against A and against C computed over `1..q*` by the same rule with `never within q*` when none exists, are reported in the family record under a `prefix` object and nowhere else, appear in no histogram, and enter no claim. Do not treat an unfinished arm's smaller work count as a speedup.

**Charges.** Reuse the checked event counters and unit increments of the earlier experiments: nine event categories (formula check, clause read, literal read, clause write, literal write, assignment, pair check, rule attempt, search node), `u64` checked increments identical in debug and release. Every charge in this protocol names its category above. Reference truth-table work, model-check work, proof-check work, and raw-checker work are outside all arms and reported separately; three enumeration ratios are computed over the 72 truth-table families only: `ratio_pair(reference_work, Σ A_j)`, `ratio_pair(reference_work, Σ P + Σ B_j)`, and `ratio_pair(reference_work, Σ C_j)`, each summed over every query of those families whether or not the run completed (an unknown run contributes its spent budget), and `null` when the denominator is zero. Every non-integer quantity is a `RatioPair` as `oracle::ratio_pair` emits it: `numerator` and `denominator` as integers and `thousandths` as the string `q.rrr` rendering the scaled integer `(numerator*1000 + denominator/2) / denominator`, rounded half up in integer arithmetic; no floating point reaches the artifact, and no wall-clock seconds or solver conflict counts do either. One signed quantity is used, defined here: a **signed thousandths difference** is the difference of two scaled integers recomputed from their `RatioPair`s, an `i64` printed as a JSON integer (for example `-37`), carried in fields named `signed_thousandths`; no other signed quantity appears, and no signed ratio is needed because every reported ratio has a nonnegative numerator.

**Bounds stated, not proved.** For a query with n variables, m₂ = b binary clauses, m clauses, and L literals: construction, components, and certificate take O(n + m) events on the query and O(n + m₂) on F; settled extraction O(n(n + m₂)) with no linear bound known ([Buss, Kullmann, and Vassilevska Williams](https://mathweb.ucsd.edu/~sbuss/ResearchWeb/DualDFS/DualDFS_SAT.pdf)); copy and appends O(L + m + n); the store read O(1); the residual DPLL has no polynomial bound. The amortized quantity `B(q)/q` is bounded below by the per-query residual, which is the unbounded term; amortization removes the build from the per-query cost and nothing else. Measured totals do not prove any of these statements, and a finite corpus proves no asymptotic bound.

**Budget and replay time.** The budget is 4,000,000 events per arm run and per persistent build, chosen so that the worst case of every run exhausting its budget stays inside the replay bound: 120 builds plus 1,920 × 3 arm runs at 4,000,000 events is `(120 + 5,760) × 4,000,000 = 23,520,000,000` events. The per-event rate is an estimate from one measurement, not a repository record: on 10 September 2026 the release binary replayed the extraction-cost artifact (`target/release/peqnp extraction <scratch path>`, byte-identical to `artifacts/extraction-cost.json`), 19,904,109 counted events (13,526,530 reference, 556,041 checker, 5,821,538 arm), in 0.40 s wall and 0.05 s user on one arm64 laptop (Apple M5 Max); by user time that is about 2.5 ns per counted event, the wall figure being dominated by process start and JSON output. The user time was read at 10 ms resolution, so the rate carries about 20 percent uncertainty. At 2.5 ns per event the worst case is about 59 s and at 3 ns about 71 s, inside the 120 s bound either way. The expected replay is far smaller. Arm events: in the extraction-cost primary random-mixed cases the baseline medians were 3,704, 5,158, and 7,238 events at n = 8, 10, 12, growing by 1.39 and 1.40 per two variables, and the maxima 6,152, 8,129, and 14,819, growing by 1.32 and then 1.82, about 1.55 per two variables over the four; extrapolating the 12-variable maximum by `1.4^4` gives about 57,000 events per arm run at 20 variables, by `1.6^4` about 97,000, and by `1.82^4` about 162,600; charging even the last ceiling to every arm run gives `3 × 1,920 × 162,600`, about 9.4 × 10⁸ events, under 3 s. Truth table: the 1,152 truth-table queries have `Σ 2^n × (b + t*n) = 129,761,280` assignment-clause pairs; in the extraction-cost artifact the reference work per assignment-clause pair was 0.371 pooled over all 338 cases (13,526,530 over 36,441,088), 0.514 as the unweighted mean over the 176 primary cases of each case's ratio, and 1.82 at most, so 4.8 × 10⁷ to 2.4 × 10⁸ events, under 1 s. The raw checker and model checks are under 10⁸ events; the LRAT checker is linear in proof text and needs under 5 s even at the file cap. **Expected replay: under 10 s in release with every component at its ceiling, bound 120 s.** The gate prints the measured wall seconds and warns over the bound; the artifact carries none of them.

## Claims and their falsification criteria

All claims are evaluated on comparable families in the forced stratum. Claim 1 is reported as `not evaluable`, never as supported, when the stratum holds fewer than 20 comparable families; Claim 2 has its own evaluability rule below. Every other reported number is descriptive, with no null hypothesis and no growth-class label; per-n rows are reported as descriptive numbers with the finite-range caveat. The break-even against arm A and the unforced stratum's break-even against arm C are accounting identities and appear under the implementation checks of acceptance, not here. Each claim is an uncertain prediction whose criterion never invalidates the run and never coincides with an acceptance condition.

1. **Amortized clues repay the read on at least half of the forced families.** Arm B's cumulative work falls strictly below arm C's within k = 16 queries on at least 500 thousandths of the comparable forced families: with N_f the number of comparable forced families and W the number among them with a break-even against C in `1..16`, the claim holds iff `W * 1000 >= 500 * N_f` in integer arithmetic. **Falsified** iff `W * 1000 < 500 * N_f`. The pooled verdict over all n, t, and b is the claim; the per-n, per-t, and per-b rows are descriptive and can neither rescue nor overturn it, and every per-family row carries the unit count u beside the break-even so that the dependence on u is visible. The pre-registered fraction rests on `artifacts/extraction-cost.json`: over the 21 primary random-mixed cases with a SAT fragment certificate, at least one derived unit, and `b = 2n`, the baseline total was 105,039 events and the settled arm's residual 57,382, so the residual saving (baseline total minus settled residual, which equals the DPLL saving less `6u`) was 454 thousandths of the baseline; the same subset of the secondary v1 corpus (21 cases) gave 112,990 against 60,841, 462 thousandths; over all forced primary random-mixed cases with b from n to 4n (57 cases) the figure was 404 thousandths, over all forced secondary v1 random-mixed cases with b from n/2 to 2n (47 cases) 380, and over the secondary cases with b from n to 2n alone (42 cases) 391; on the `b = n` subsets it was 365 (primary, 28 cases) and 318 (secondary, 21 cases). With the build paid once, the per-query margin M of `241 + 9u` to `1,001 + 9u` events must be beaten by that saving, and a saving of 400 thousandths of the smallest baseline median, 3,704 events, is about 1,480 events per query, so the fraction is expected to hold with room, the build P being recovered over the remaining queries; where it could fail is the `b = n` families, whose units are fewer and whose saving was smallest on the earlier corpus, and families whose few units barely shorten the DPLL. By the pre-freeze simulation 25 of the 46 forced families have `b = n` and most of those carry one to three units, so the pooled verdict rests largely on whether one to three units repay about 250 to 790 events per query (M at `b = n` from `n = 8, t = 3, u = 1` to `n = 20, t = 4, u = 3`) plus P. The break-even histogram carries the finer information either way, and if the claim fails the per-n and per-b rows say where.
2. **The persistent arm's DPLL ratio does not fall relative to the plain baseline, arm C, across n.** For each n, over the comparable forced families at that n **with `b = n`**, compute the three ratios of the decomposition above: `r(n)`, `m(n)`, and `r_d(n)`. One fixed binary-count composition is used because the forced stratum's mix of b shifts with n by construction of the generator (at `b = 2n` and `b = 3n` the fragment is unsatisfiable or heavily forced at large n far more often than at n = 8, and families with more forced units save more residual work, so a ratio pooled over b would move with composition alone), and `b = n` is the composition present at every n. An n is **evaluable** when it has at least 4 comparable forced families with `b = n`, half of the 8 families drawn per n at that b; the claim is evaluable when at least three n are evaluable, and is otherwise reported as `not evaluable`. By the pre-freeze simulation the `b = n` forced counts are 2, 4, 5, 7, 7 at n = 8, 10, 12, 16, 20, so n = 8 is expected not to be evaluable by construction, n = 10 sits exactly at the floor, and the crate's counts are reported whatever they are. The same three ratios pooled over all forced families, and per `(n, b)` for every b, are reported as descriptive rows that can neither rescue nor overturn the claim. Let `n_1 < ... < n_e` be the evaluable n and `d(n, n')` the signed thousandths difference `scaled(r_d(n')) - scaled(r_d(n))`. The claim is registered on `r_d`, not on `r`, because the margin term `m(n)` falls with n by construction and is not the phenomenon. The claim holds unless the DPLL ratio falls substantially and stays down: **falsified** iff `d(n_1, n_e) <= -250`, `scaled(r_d(n_e)) <= scaled(r_d(n))` for every evaluable n (a tie with an earlier value counts as the minimum), and no consecutive `d(n_i, n_{i+1})` exceeds `+50`; one integer test with three conjuncts, so that a single uptick of a few thousandths inside a fall of 250 or more does not rescue the claim, while a rebound of more than 50 or a final value that is not the minimum does. Focused tests fix the rule on hand-made series: `900, 700, 705, 600` falsifies (fall 300, uptick 5, minimum last); `900, 650` falsifies (fall exactly 250); `900, 700` does not (fall 200); `900, 600, 700, 650` does not (rebound 100, last not the minimum); `900, 640, 700, 600` does not (fall 300 and minimum last, but a rebound of 60); `900, 600, 600` falsifies (fall 300, tie at the minimum, no rebound). The bar of 250 thousandths is set from the analogous quantity on the earlier corpus, recomputed before the freeze from `artifacts/extraction-cost.json` on the primary random-mixed cases with a SAT certificate and at least one unit, where `(residual - 6u)` of the settled arm over the baseline total is the single-shot analogue of `r_d`: pooled over b it was 606, 648, and 544 thousandths at n = 8, 10, 12 (21, 17, 19 cases), movements of +42 and -104, a net fall of 62 and a sum of absolute movements of 146; on the `b = n` cases alone it was 721, 751, and 532 (6, 11, 11 cases carrying 11, 18, 39 units), movements of +30 and -219, a net fall of 189 and a sum of absolute movements of 249. The bar exceeds every adjacent movement and every sum of absolute adjacent movements observed on those subsets, so no single swing of the size that corpus showed can produce a falsification here; a bar of 150 would have been crossed by the `b = n` fall of 189 over two steps. Extrapolated per step over the four steps from n = 8 to n = 20, the pooled trend reaches about -124, under the bar, and the `b = n` trend about -378, over it, so the earlier data leave the outcome open, and the registered expectation is stated as open rather than as holding: the amortization argument, with the identity `B_j = A_j - P - 6*t*n + 1` showing that the persistent arm's per-instance cost is the fresh arm's less a per-family constant, predicts a bounded ratio, while the earlier `b = n` cases fell with n as their unit counts rose. That last point is the confound the fixed composition does not remove: within `b = n` the unit count per family still varies with n by the generator's draws (the simulated series above), and families with more units save more residual work, so a falling `r_d` can come from unit composition alone; the per-n rows carry the unit counts beside the ratios and no claim corrects for it. If the claim is falsified, the artifact reports beside `r_d(n)` the descriptive per-n rows of P, `store_cells`, and u, so that the build and length of the store are visible next to the falling ratio; the finding is a reason to measure how the build and the store grow, and it is not evidence about any complexity class, because arm A reaches the same per-instance cost by rebuilding the store at charged polynomial cost on every query. Per-n `r(n)` rows are also reported descriptively for the `unforced` stratum, where `r(n)` exceeds 1 by construction, and for the `fragment-unsat` stratum, where `B_j = 1` and the ratio is `16 × families / Σ C_j`, falling with n by construction because a decided fragment answers every query from the store; neither carries a claim.

The `fragment-unsat` stratum carries no claim. It is reported with the same completeness: break-evens against A and C, cumulative curves, and the note that on these families arm B's per-query work is 1 and arm A's is the three graph phases, so amortization only widens a win the fragment-interface experiment already recorded for the single-shot certificate. No required result is a positive delta; a negative result on any claim is reported with the same completeness as a positive one.

**Pre-freeze observations.** No arm, reference evaluator, oracle, or checker ran on any query or fragment of this corpus before the freeze, so no DPLL cost, label, break-even, or ratio of this corpus was observed. Four design-time computations did run, and their results are the only numbers above that were seen before the freeze: (1) the generator reimplementation with the transitive-closure classifier, which observed the stratum counts, the per-n and per-b counts, the unit counts of the forced families, and the absence of repeated remainders stated in the corpus section, all of which bear on the evaluability of both claims and on the expected failure modes but on no arm cost; (2) the generator run with placeholder counters of the artifact's digit widths that produced the byte estimate under the size budget, and the part-inflation measurement stated there, one 786,432-byte part of extraction-cost rows and one of placeholder records in this protocol's layout, each wrapped in the operation shape of `ledger/pages/0003.json` and pretty-printed as `scripts/oh-snapshot.mjs` does; (3) the recomputations from the committed `artifacts/extraction-cost.json` quoted under Claim 1, Claim 2, and the replay-time paragraph, which are data of an earlier corpus; and (4) the one timing of the extraction-cost replay. The claims were specified before the frozen corpus was run by the implementation, with those observations in view.

## Acceptance

A violation of any implementation check invalidates the calibration; repair implementation bugs transparently before publication, preserving the frozen design. Algorithm, corpus, budget, limit, or claim changes prompted by observed performance require a new protocol identity. Artifact layout may be compacted without dropping or altering any reported quantity.

**Implementation checks.** The theorems, accounting identities, and consequences of the fixed corpus and charge table below are not claims; a violation is an implementation defect.

- **Labels.** Every completed decision of every arm on every query agrees with the reference where the label is `sat` or `unsat`. A truth-table label is `sat` iff the model count is positive iff a backbone exists. An oracle `sat` label has a checked model, an `unsat` label a checked proof; a `definition` row is an error in this corpus. After the corpus, every answer-file entry has been used and no entry is missing; with the 768 distinct digests this is use by exactly one query each.
- **Budgets.** No arm run exceeds its budget; an unknown run spent exactly the budget and reports no certificate, clue, unit, or outcome. The per-query totals equal the sums of the reported phases.
- **Store identity.** For every family whose build completed, and for every query on which arm A completed: arm A's certificate equals the stored certificate; arm A's clue list equals the stored clue list in literal, order, and path (nodes and cited clause indices); arm A's derived units equal the stored units in order. Arms A and B therefore derive identical units per family. Arm A's construction work equals the persistent construction work plus `6*t*n`; its components, certificate, and extraction counters equal the build's. `store_cells` equals the definition above and is at most `n + 4n²`.
- **Per-query identities.** In the `fragment-unsat` stratum: arm A, when it completes, returns UNSAT with extraction, append, and residual idle, and arm B's per-query work is exactly 1. In the satisfiable strata, when arms A and B both complete a query: arm B's append and residual counters equal arm A's, and arm B's total is `1 + append + residual`. In every stratum, when the build and arms A and B all complete: `B_j = A_j - P - 6*t*n + 1`. In the `unforced` stratum, when arms B and C both complete a query: their residual counters are identical and `B_j = C_j + 1 + 6b + 8*t*n`; when arm A also completes that query, its residual equals theirs.
- **Cumulative identities.** On every comparable family: `B(q) = A(q) - (q - 1)*P - q*(6*t*n - 1)` for every q in `1..16`, and the break-even against A equals 1; on every comparable `fragment-unsat` family additionally `B(q) = P + q` and `A(q) = q*(P + 6*t*n)`. On every comparable `unforced` family: `B(q) - C(q) = P + q*(1 + 6b + 8*t*n)` for every q, and the break-even against C is `never within k`.
- **Ratio decomposition.** On every set of comparable forced families over which the three ratios are reported: `numerator(r) = numerator(r_d) + numerator(m)` with the common denominator `S_C`, the checked subtraction `S_B - S_M` does not underflow, and every `RatioPair` thousandths string equals the integer rounding of its pair.
- **Checker.** A raw-clause checker outside all arms validates the stored certificate and every stored path against F once per family, and arm A's certificate and every arm A path against the query formula on every query; every validation passes and the counts of checked and valid certificates and paths match the arms' reported counts. On truth-table satisfiable queries the stored units are a subset of the query's backbone with no repetition. On oracle satisfiable queries the checked model makes every stored unit true.
- **Isolation.** The focused test that runs a family's queries in a permuted order reproduces every per-query outcome and counter of the protocol order.
- **Corpus.** 120 families and 1,920 queries in the stated order; pairwise-distinct remainders; `exact_earlier_overlap: 0` from the comparison against all six earlier corpora and the demo fixtures; 768 oracle queries and 768 answer-file entries; no fragment formula in the oracle corpus list. The crate's stratum counts are reported beside the pre-freeze expectations of the corpus section; a difference between them is examined against the stated generator rules before publication and reported with the crate's counts, which stand.

**Reporting.** Keep every generated fragment and remainder, every outcome, phase counter, stored certificate, clue with path, cumulative sequence, break-even, ratio, signed difference, and comparison. Each family record carries its fragment clauses once, the store with full paths and `store_cells`, the unit count u, the full nine-category `Work` of every build phase, the cumulative arrays, the break-evens, the comparable prefix and its `prefix` values where the family is not comparable, and its stratum or the `build-unknown` bucket; the 1,920 query records form the artifact's top-level `observations` array in corpus order, the array the records script splits into parts, and the family records and aggregates are the non-observation remainder; each query record carries its remainder clauses only (the query is `F ++ R_j` by the stated layout), its label object in the reference-oracle artifact format with the nine-category checker `Work` the shared validator requires, the outcome and per-phase `work_units` and search nodes of each arm, and arm A's derived units. The ledger validator for this experiment reconstructs each query's input as the family's `fragment` followed by the record's `remainder` before it computes `dimacs_sha256` with the exact `write_dimacs` layout, before it checks an oracle model against the clauses, and before the raw-checker and backbone checks; nothing is hashed or checked against a remainder alone. Full nine-category breakdowns appear at the family, stratum, per-n, per-b, per-t, and summary levels. Report strata before aggregates, and within each stratum the histogram of break-evens against A and against C over `1..16` and `never within k`, counting comparable families only, the counts of non-comparable families by reason and by arm, and the per-n, per-b, and per-t subtotals. ## Limitations

- Amortization is not worst-case complexity. A break-even at q queries states that, for this family and this event model, the build was repaid after q related instances; it bounds nothing about one instance, and the per-query residual, which has no polynomial bound, is untouched by persistence.
- The persistent store is exactly the advice model if it were allowed to depend on n rather than on the fragment: a store supplied per input length would be P/poly, and Karp and Lipton's collapse is the reason that route is believed closed. Here the store is built by an arm from an input at charged cost, which is why its build appears in `B(q)`, and the fresh arm rebuilds it per query at that same charged cost, which is why the identities above hold.
- Claim 2 is a finite-range test on at most five values of n with pseudorandom families; a ratio that holds or falls here says nothing about the limit, and the `fragment-unsat` stratum shows a ratio that falls by construction because the store holds the answer. Fixing `b = n` removes the b-composition confound but not the unit-composition confound: the unit count per family still varies with n by the generator's draws, and the claim does not correct for it. A falling DPLL ratio in the forced stratum would be a reason to measure the store's build and length next; the framework's reading is that with a polynomial build a fresh algorithm obtains the same per-instance cost inline, which arm A demonstrates on this corpus.
- Family exclusion is all-or-nothing and biased in a known direction. A family drops from the claims when any arm exhausts its budget on any of its 16 queries or when a label is unknown, so the probability that a family is comparable compounds over 16 queries. Arm C exhausts where the residual is largest, which is where arm B's saving would be largest, and arm A exhausts before arm B on identical residuals because it has spent `P + 6*t*n` more events per query; exclusions therefore remove families in the direction that favours arm C in Claim 1 and can remove the largest n, or n = 10 at its floor of 4, from Claim 2. The per-arm exclusion counts per stratum and per n and the comparable-prefix values make the size and direction visible; no claim corrects for it.
- The fragment and its indices are given to arm B by the family's construction; arm B does not verify per query that the query contains the fragment. The harness's layout invariant, checked outside the arms, carries that assumption. A deployment that had to discover a shared fragment would pay a recognition cost this protocol does not measure.
- The k remainders share nothing with each other beyond the fragment; the corpus does not model queries that share ternary structure, learned clauses, or partial assignments, and the store deliberately carries none of those.
- Calibration of a known interface with a toy DPLL: no novel inference rule, no evolutionary advantage, no ranking of competitive solvers, no general SAT complexity result, and no P versus NP claim.
- Finite fixed corpus at 8 to 20 declared variables and clause width at most three; pseudorandom families are reproducible samples, not independent or representative population estimates; the strata are determined by the generator's draws and are unbalanced across b.
- Declared event counters exclude allocator internals, loop control, arithmetic and comparison instructions, corpus generation, JSON formatting, and report construction; they are operational measurements, not elapsed time or a proved bit-cost bound.
- Above 12 variables the label is a pinned solver's answer certified by a checked model or a checked LRAT proof; the certificate is the evidence, the solver is not, and a conflict-limit unknown is unknown. Oracle cost is outside the event model and is not reported.
- Budget exhaustion means unknown and excludes the family from comparisons. It is not expected: the extraction-cost baseline medians of 3,704, 5,158, and 7,238 events at n = 8, 10, 12 grew by about 1.4 per two variables and the maxima of 6,152, 8,129, and 14,819 by 1.32 and then 1.82, so the 20-variable maximum extrapolates to about 57,000 events at 1.4 per two variables, 97,000 at 1.6, and 162,600 at 1.82, against a budget of 4,000,000; the number of excluded families is nevertheless a reported result.
- A fragment SAT certificate is an assignment of the fragment, not a model of the query. UNSAT queries have no defined backbone; the subset check on units applies to satisfiable queries only.

## Primary references

- [Karp and Lipton, Some connections between nonuniform and uniform complexity classes (1980)](https://doi.org/10.1145/800141.804678): Turing machines that take advice; if NP had polynomial-size circuits the polynomial hierarchy would collapse to its second level.
- [Arora and Barak, Computational Complexity: A Modern Approach, chapter 6](https://theory.cs.princeton.edu/complexity/book.pdf): Boolean circuits, P/poly, and the circuit-advice equivalence that places length-indexed persistent knowledge in the non-uniform class.
- [Knowledge, clues, and computational complexity](../docs/knowledge-and-complexity.md): the repository's framework, in particular the section on loading, persistence, and what counts as a step, the interface delta this experiment amortizes, and the build, length, and residual-ratio description of a persistent library that Claim 2 tests.
- [Darwiche and Marquis, A Knowledge Compilation Map (2002)](https://www.cs.cmu.edu/afs/cs.cmu.edu/project/jair/pub/volume17/darwiche02a.pdf): offline compilation for repeated cheap queries (the phrase compile once, query many is this protocol's paraphrase, not their term); representation size, supported queries, and supported transformations as the three separate concerns.
- [Aspvall, Plass, and Tarjan (1979)](https://doi.org/10.1016/0020-0190(79)90002-4) and [Buss, Kullmann, and Vassilevska Williams (2024)](https://mathweb.ucsd.edu/~sbuss/ResearchWeb/DualDFS/DualDFS_SAT.pdf): the fragment decision and the complete 2-CNF backbone bound inherited by the persistent build, unchanged from the extraction-cost protocol.
